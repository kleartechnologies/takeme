# TAKEME Intelligence V1 — web and Flutter contract

Phase 6 is a deterministic organic discovery foundation, not a prediction or paid-ranking system. The source of truth for policy is `functions/src/intelligence-domain.ts`; both web and future Flutter clients use the same regional Firebase callable API (`asia-southeast1`). Do not port the ranking formula into UI code. Phase 7 adds a separate [paid placement layer](mobile-monetization.md) without changing organic scores.

## Event architecture and privacy

The client sends semantic intent to `trackMarketplaceEvent` with Firebase Auth. The callable derives `userId`, listing category, seller, price, location, condition and type on the server; clients cannot set these values. `marketplaceEvents/{sha256(user|type|scope|window)}` stores `userId`, `eventType`, `source`, optional listing/category/seller/query/price/type, optional `context`/`candidateSource` and impression listing IDs, plus server `createdAt` and `expiresAt`. It never stores private messages, payment details, tokens or profile email. Source and context on low-trust client attribution are diagnostic metadata, not proof of display.

Allowed client events: `VIEW_LISTING`, `AUCTION_VIEW`, submitted `SEARCH`, `CATEGORY_VIEW`, `FILTER_APPLIED`, `SHARE_LISTING`, `PROFILE_VIEW`, `SELLER_VIEW`, `RECOMMENDATION_IMPRESSION`, `RECOMMENDATION_CLICK`, `NOT_INTERESTED`. The web currently emits the relevant view/search/category/filter/share/seller/recommendation events; `PROFILE_VIEW` and explicit `NOT_INTERESTED` are contract-ready but have no UI action yet. `SAVE_LISTING`/`UNSAVE_LISTING` come from Saved document triggers, `BID` from authoritative bid creation, `MESSAGE_STARTED` from conversation creation, and `MESSAGE_SENT` from a buyer's message document. A seller reply does not boost their own item. Phase 7 adds private promotion request/engagement events separately; purchase and revenue events still require verified payment. No GMV is fabricated.

Client view dedupe is 30 minutes, recommendation click 10 minutes, other client intents one hour per scope; at most 100 accepted client events per user-day. One transaction atomically creates an event, updates the bounded interest profile and listing trend (when positive), and increments quota. Authoritative triggers use their event ID for retry-safe dedupe. `marketplaceEvents` retention is intended to be 90 days; configure Firestore TTL on `expiresAt` before production. Quota documents have a 3-day TTL. TTL is not a guaranteed immediate deletion mechanism. No scroll, hover, keystroke, or animation events are collected. Raw events and interests are readable only to an authenticated `admin` custom claim (bounded event lists); all client writes are denied. Regular clients cannot read raw behavior, interests, trend scores or quotas, including their own.

## Interest and ranking

`userInterests/{uid}` holds bounded category (20), price band (5), seller-stated location (10), listing type (3), condition (4), recent normalized searches (5), and repeated-exposure counts (32). No GPS or subcategory is inferred because listings do not supply an authoritative subcategory. A 30-day half-life decays interest, including at read/rank time. Central weights: view/category/filter +1, search +3, save +6, bid +8, conversation start +7, buyer message +2, share +3, recommendation click +3; unsave -3 and explicit not-interested -4. An impression has no immediate negative interest; repeated exposures gradually subtract ranking points. All components are capped.

`getMarketplaceRecommendations` returns `{version:"v1", mode:"discovery"|"personalized", items:[{listing,candidateSource}]}` with at most eight active, non-self listings. V1 candidate generation reads at most 16 recent listings, two strongest categories × eight listings, 12 recent trend records and their listing documents, and the latest 12 Saved IDs. Candidates are deduplicated before ranking. The recent and category queries reuse marketplace facet indexes; trend query uses its `updatedAt` single-field index. The trend score decays with a seven-day half-life and only trends updated in the last seven days are candidates. No full-database scan or global realtime listener is used. Auction listings participate when active; no unsupported combined-buy flow is invented.

The bounded organic score is category affinity (-8..18) + price (-4..8) + seller-stated location (-4..8) + listing type (-3..5) + condition (-2..4) + recent search/title match (0..6) + freshness (0..10) + listing completeness (0..6) + trend (0..10), minus repeated exposure (0..10) and already Saved (8). Category diversity adds a selection-stage adjustment: up to two items per category while alternatives exist. Ties resolve by recency and ID. Inactive listings are excluded. Trust contributes **zero** until verified reputation exists; paid promotion contributes nothing. Completed-purchase exclusion is deferred because no authoritative completed purchase flow is active. Scores/components are internal and never returned to the client.

Personalized mode requires at least three accepted events, one meaningful search/save/bid/conversation/click event, and a decayed category score of at least 1.5. Until then, the same endpoint provides recent/trending discovery and the UI retains “Top Picks”; only personalized mode displays “Recommended for You”. If the new callable is unavailable, web falls back to its existing bounded recent feed rather than pretending personalization succeeded.

“Similar items” on detail queries at most 16 active listings from the same category and ranks by category, relative price, shared title words, type and condition. It excludes the current listing and shows at most four cards (up to eight returned by the client service). It has loading, empty and retry states. No embeddings or LLM calls are involved.

## Admin analytics preparation

The private event log, `candidateSource` and `context` support future counts by event type, category, search query, listing and recommendation source, plus impressions and clicks. User and listing counts should come from authoritative Auth/listing collections; active-user windows can use distinct authenticated event users once a bounded aggregate pipeline is built. A future dashboard will need separately defined aggregation, retention and index strategy, and should not query the entire raw event collection in a browser. Search result/zero-result counts are **not yet recorded**. A save following a recommendation is not yet causally attributed, and impressions/clicks are observational rather than proven conversions. Completed transactions, GMV, average transaction value, Boost and Featured revenue are unavailable until authoritative transaction/payment systems exist. Listing price and bid value are never GMV.

## Cost, abuse and rollout

One accepted client event costs a small Firestore transaction (event/profile/quota and optionally trend); a duplicate still incurs reads but no writes. Triggers create events only after authoritative state transitions. Per-user quotas and time buckets reduce accidental write amplification, but are not a substitute for abuse monitoring or App Check. The recommendation read path is bounded to roughly 16 + 16 category + 12 trends + 12 trend listings + 12 Saved documents, plus one profile; overlap reduces unique candidates. Firestore indexes required by the event collection are `(eventType, createdAt)` and `(userId, createdAt)`; existing marketplace indexes remain unchanged. Check actual production usage and quotas before scale-up. No scheduled aggregation or external ML service is added.

Before a separately approved rollout, deploy and verify Firestore rules/indexes **and** the seven new Functions together, then enable TTL for `marketplaceEvents.expiresAt` and `intelligenceQuotas.expiresAt`. Confirm the deployed function region, index readiness, IAM, billing, App Check policy, monitoring and consent/retention policy. Do not deploy from this phase. Local verification uses `demo-takeme` emulators only: `node tests/intelligence-emulator.integration.mjs` with Auth, Firestore and Functions emulators; `npm run test:functions`, `npm test`, lint, strict TypeScript, and build.

## Flutter translation

Flutter should invoke the same callables with Firebase Auth and use the returned `mode`, `items` and `candidateSource` to render the same Top Picks/Recommended states. Track submitted search and meaningful taps only; throttle navigation-driven listing views and batch up to eight impression IDs by source/context when cards actually become visible. Do not write event/profile/trend documents directly, trust client clocks or replicate ranking in Dart. Use the same two-column compact cards, category discovery, touch targets, skeleton/empty/error states, and explicit auction labels described in [mobile marketplace patterns](mobile-marketplace-patterns.md). A future V2 can replace server candidate generation/ranking behind the versioned callable response without rewriting native feed widgets.
