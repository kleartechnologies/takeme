# TAKEME Discovery 2.0

Discovery is a deterministic, server-ranked marketplace surface. It extends the Phase 6 interest model; it does not use an LLM, device GPS, paid placement as an organic signal, or client-calculated scores. `functions/src/intelligence-domain.ts` owns the policy, `functions/src/discovery.ts` owns bounded candidate generation and section assembly, and `/for-you` renders the server response.

## API and mobile contract

`getMarketplaceDiscovery({ sectionId?, cursor? })` requires Firebase Auth and returns `{ sections, sessionId, metadata }`. Each section has `id`, `title`, `reason`, `type: "listing_rail"`, up to four `{ listing, candidateSource }` items, and `nextCursor`. Metadata has `personalized`, `generatedAt`, and `version: "v2"`. Initial fetch omits both inputs. To page one section, send its `id` and returned cursor; offset is a bounded integer 0–16. Do not interpret it as an all-marketplace cursor. Inventory may change between requests, so clients should deduplicate by listing ID. The first response does not return the whole candidate pool or any score, private interest, search history, or ranking weights. Empty sections are omitted.

`getMarketplaceSimilar({listingId})` returns up to eight server-ranked active listings and a discovery session for an authenticated caller. The older `getMarketplaceRecommendations` home contract remains available, now version `v2` with a session. Flutter and web should call the same regional Functions, render the section order and reasons provided, and use native horizontal rails / compact cards rather than reimplementing ranking. Both can show loading skeleton, empty, error/retry and signed-out states. Touch targets are at least 44 logical pixels. The bottom navigation remains Explore / For You / Sell / Updates / Me.

## Candidate generation and performance

One discovery request reads at most 24 recent listings, 16 active auction listings, 16 recent trend records, up to 28 referenced trend/recent-view listing documents in one `getAll`, two strongest categories × 12 active listings, 12 Saved IDs, and one user profile and interest document. IDs are deduplicated before scoring. No seller-by-seller reads, unbounded collection scans, realtime listener, or global user-behavior query is made. The category/recent queries reuse the existing `(status, facetKeys, createdAt)` index; the auction query reuses `(status, auctionStatus, auctionEndAt)`. Trend records use an indexed `updatedAt`. Admin section counts use `(eventType, sectionId, createdAt)`; deploy that index with Functions and rules in a separately authorized rollout. Query counts remain bounded on section pagination, though each page regenerates the bounded candidate pool. A future scale optimization could cache a short-lived pool, but should keep served-item authorization separate.

Candidate sources are personalized categories, recent listings, decayed recent trends, live auctions, and private recently-viewed IDs. Saved items affect ranking and category interest but are not a standalone public lane. Similar listings have a separate 24-item same-category query. Location is only the explicit general location in the user's public profile, matched to a seller-stated listing location; there is no GPS, distance claim, or inferred precise location. `Popular in {location}` appears only if that location has candidates with real trend activity. No local section appears otherwise.

The first screen can contain For You, Because You Like, Popular in your stated location, Popular Right Now, Just Listed, Auctions You May Like, and Recently Viewed. Sections require real eligible inventory and are omitted when empty. First-page items are deduplicated across sections; later pages can overlap as inventory changes, so the client deduplicates within its section. Free/giveaway inventory is unsupported because listings require a positive price. Price Drops is intentionally absent: the current listing schema has no authoritative price-change history, so a drop cannot be verified. A future price-drop lane needs immutable server-authored before/after price records and rollback/fraud policy.

## Ranking, cold start, and diversity

The existing 30-day half-life applies to category, price band, seller-stated location, listing type, condition and exposure affinities. Search terms are normalized and bounded to five recent queries. Category (20 keys), price (5), location (10), listing type (3), condition (4), exposure (32), hidden listings (32), and recent views (12) are bounded. Positive signals include real views, search, save, bid, buyer message, recommendation click and completed transaction. A completed transaction is a strong signal (weight 12, capped to 8 per signal update) but only after authoritative status verification. Pending, cancelled or disputed transactions do not update interests. One view does not turn on personalization: at least three accepted signals, one meaningful action, and decayed category affinity >= 1.5 are required.

Candidate scoring remains server-only: bounded affinities, title/query match, freshness, listing completeness and seven-day decayed trend, minus already-Saved and repeated-exposure penalties. Trends count accepted, deduplicated signals; raw views have low weight and each user has a daily event cap. No paid promotion field enters the score. Ties resolve deterministically by score, recency, then ID. The selector prefers at most two listings per category and seller while alternatives exist, then relaxes those limits to fill available inventory. Inactive, own, invalid-price and elapsed/cancelled auctions are excluded. Cold start uses quality/freshness/trend without claiming personal interest or inventing a location.

Seller reputation is shown in the shared listing card from the separate verified trust system. It does not currently alter organic ranking: a neutral trust weight avoids extra seller lookups and prevents unverified or missing trust data from silently influencing discovery. Promotions remain in their existing separate placement system, visibly labeled; Boost and Featured do not modify interests, trust, trends or organic scores. Auction labels and timing use authoritative listing state and timestamps, never fabricated urgency.

## Impressions, negative signals, and attribution

Each recommendation response creates a private server-owned, two-hour `discoverySessions` document containing only the IDs actually returned, their source, section and reason. A client impression/click must present the session ID. The callable verifies ownership, expiry and served IDs before accepting it; client-supplied source/reason is rejected. The shared ListingCard reports one impression only when the individual card reaches 35% visibility, not when a feed wrapper appears. Deduplication and a 100-event/day user cap avoid per-render writes. Repeated ignored exposure subtracts at most ten ranking points and decays; a click clears that listing's repetition penalty.

"Not interested" is a listing-level action with an Undo control. It hides only that listing for at most 30 days; it does not subtract category or price affinity. `INTEREST_RESTORED` removes the hide. Both are private, bounded user signals. The UI optimistically hides/undoes and rolls back on errors. There is no unsupported category-level dismissal or reason selector.

An accepted recommendation click records a seven-day private `discoveryAttributions` record. If the same user later saves that listing, the authoritative Saved trigger copies the verified section/source/reason to the Saved event. This establishes "save after a discovery click", not that discovery caused the save or a later transaction. Admin Intelligence reports per-section card impressions, clicks and attributed saves, plus event counts. It does not claim a recommendation CTR or purchase funnel, because clicks can precede impression delivery and completion cannot yet be attributed to a discovery session.

## Similar, auctions, privacy and security

Similar results use category, relative price, shared title tokens, listing type and condition. They exclude the reference listing, its seller, the requesting user's own listings, inactive inventory and elapsed auctions. Recently Viewed comes from a private, 12-ID bounded list updated only on accepted listing/auction views; missing or inactive items are filtered on fetch. `userInterests`, raw events, trends, sessions, attributions and completion ledgers are server-written. Firestore rules deny client writes to all of them, and ordinary users cannot read other users' behavior. Sessions do not expose ranking internals. Event records have 90-day expiry; configure TTL for new session/attribution records before rollout as well. Server credentials and exact location are never returned in discovery metadata.

The trusted completion trigger checks the corresponding transaction is actually `completed`, has the same buyer/listing/category and a valid integer amount, then idempotently updates only that buyer's interest through `intelligenceCompletions`. It does not trust a client-declared purchase, mark an auction winner as buyer, or affect payment settlement. A pending transaction event is ignored.

## Verification and rollout boundary

Local checks: `npm run test:functions`, `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`, and `node tests/intelligence-emulator.integration.mjs` against the `demo-takeme` Auth/Firestore/Functions emulators. Validate narrow/mobile and desktop `/for-you` states, card visibility, Undo, and section pagination with actual emulator listings. Before any separately authorized production rollout: deploy Functions, rules and the new index together; configure TTL for `marketplaceEvents.expiresAt`, `intelligenceQuotas.expiresAt`, `discoverySessions.expiresAt`, and `discoveryAttributions.expiresAt`; verify index readiness, App Check/rate limits, monitoring, billing and privacy policy. This phase performs no deploy or push and creates no production listings.
