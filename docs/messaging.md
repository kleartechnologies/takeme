# Marketplace conversations

Phase 14B uses the existing `conversations/{listingId}_{buyerId}` collection and its `messages` subcollection. A conversation is unique per buyer and listing. It records listing/buyer/seller IDs, participant IDs, optional transaction ID, listing title/image context, status, timestamps, a short last-message preview and per-participant unread counts. A message stores server-derived sender ID, normalized plain-text body (1–2000 characters) and server timestamp. No attachments, read receipts, payment credentials or provider references are stored.

Authenticated buyers open an active, eligible, non-self listing via `openListingConversation`. The call checks the listing and uses a Firestore transaction for idempotency. `openTransactionConversation` checks transaction membership and attaches the same thread to a legitimate deal, including after listing deactivation; the transaction-created trigger also performs this handoff. A cancelled transaction does not delete its conversation. Only the buyer and seller can use conversation callables; direct Firestore reads/writes are denied, including to admins through client SDK rules. Admins receive bounded reported-message context only through `getAdminRecord` after claim authorization. Participants cannot choose sender, participant, listing or transaction IDs on writes.

The inbox fetches 20 conversations per page, and a thread fetches 20 messages per page. No global listener or unbounded history is used. Sending emits an existing in-app `message_received` notification to the other participant, subject to their notification preference. The mobile contract is a listing-context inbox row, private thread header, chronological messages and a 44px-or-larger composer action. There is no presence, typing indicator or rich media.

Reports for conversations and messages use the existing `reports` collection through `submitMarketplaceReport`. Only participants can report them, and message reporters cannot report their own messages. The deterministic reporter-target ID prevents repeated spam reports. Admin report detail can view the reported message and up to 20 recent context messages, then record status, resolution and private internal notes. These notes are never returned through user callables.

## Current privacy and retention behavior (not a final policy)

- `getConversation`, `getConversations` and `getConversationMessages` require Firebase Auth and check that the caller is the stored buyer or seller. `sendConversationMessage` and `markConversationSeen` perform the same check. Firestore rules deny all direct conversation/message access, including direct admin-client access. Sender ID and timestamps come from the server, not the caller.
- A listing must be active and eligible to **start** a listing conversation. An existing conversation remains readable and sendable after the listing becomes inactive. A verified transaction can attach or access the same buyer/listing thread after deactivation; it does not create a second thread. Transaction completion, cancellation and dispute do not currently close or delete a thread. The send callable only rejects a conversation explicitly marked `closed`; this implementation does not provide a user-facing close or reopen action or automatically set that status.
- Users currently have no delete, edit, export or retention-setting control for messages or conversations. There is no TTL, scheduled purge or account-deletion cleanup for them. Deleting or deactivating an Auth account is not implemented here as a conversation lifecycle: the stored history, participant IDs and listing/transaction context would remain, while the removed account could no longer authenticate to use participant callables. Do not promise automatic erasure or continued account access.
- Firestore retains the conversation document (including short latest-message preview, unread counts and timestamps), full message bodies and sender IDs in its `messages` subcollection, and any submitted moderation reports with reporter/target IDs, reason, details, status, resolution and private notes. An in-app notification stores listing context and a generic message notice, not the message body. Marketplace intelligence may retain a message-started/sent **event without the message body** under its separately documented event retention behavior.
- Claim-authorized admins can inspect a reported conversation through the admin report-detail callable, which returns the reported message and at most 20 recent messages. This is moderation access, not unrestricted direct Firestore client access. Participants cannot read report state or internal notes. Backend operators with Admin SDK/IAM access remain outside client-rule restrictions.

No legal retention period, deletion/export right, account-closure handling or abuse-review process has been finalized in code. Privacy/legal/product review and a user-facing disclosure are production prerequisites. This is not end-to-end encrypted messaging.
