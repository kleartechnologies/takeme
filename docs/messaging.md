# Marketplace conversations

Phase 14B uses the existing `conversations/{listingId}_{buyerId}` collection and its `messages` subcollection. A conversation is unique per buyer and listing. It records listing/buyer/seller IDs, participant IDs, optional transaction ID, listing title/image context, status, timestamps, a short last-message preview and per-participant unread counts. A message stores server-derived sender ID, normalized plain-text body (1–2000 characters) and server timestamp. No attachments, read receipts, payment credentials or provider references are stored.

Authenticated buyers open an active, eligible, non-self listing via `openListingConversation`. The call checks the listing and uses a Firestore transaction for idempotency. `openTransactionConversation` checks transaction membership and attaches the same thread to a legitimate deal, including after listing deactivation; the transaction-created trigger also performs this handoff. A cancelled transaction does not delete its conversation. Only the buyer and seller can use conversation callables; direct Firestore reads/writes are denied, including to admins through client SDK rules. Admins receive bounded reported-message context only through `getAdminRecord` after claim authorization. Participants cannot choose sender, participant, listing or transaction IDs on writes.

The inbox fetches 20 conversations per page, and a thread fetches 20 messages per page. No global listener or unbounded history is used. Sending emits an existing in-app `message_received` notification to the other participant, subject to their notification preference. The mobile contract is a listing-context inbox row, private thread header, chronological messages and a 44px-or-larger composer action. There is no presence, typing indicator or rich media.

Reports for conversations and messages use the existing `reports` collection through `submitMarketplaceReport`. Only participants can report them, and message reporters cannot report their own messages. The deterministic reporter-target ID prevents repeated spam reports. Admin report detail can view the reported message and up to 20 recent context messages, then record status, resolution and private internal notes. These notes are never returned through user callables.

Messages currently have no automatic deletion or legal retention guarantee. Deactivation and cancellation preserve history for coordination/disputes unless a future reviewed retention policy changes it. Privacy/legal review is required before production rollout, including retention period, deletion/export rights, moderation access, abuse handling and user disclosure. The present implementation does not constitute encrypted end-to-end messaging.
