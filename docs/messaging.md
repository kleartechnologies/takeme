# Marketplace conversations

Phase 14B uses the existing `conversations/{listingId}_{buyerId}` collection and its `messages` subcollection. A conversation is unique per buyer and listing. It records listing/buyer/seller IDs, participant IDs, optional transaction ID, listing title/image context, status, timestamps, a short last-message preview and per-participant unread counts. A message stores server-derived sender ID, normalized plain-text body (1–2000 characters) and server timestamp. No attachments, read receipts, payment credentials or provider references are stored.

Authenticated buyers open an active, eligible, non-self listing via `openListingConversation`. The call checks the listing and uses a Firestore transaction for idempotency. `openTransactionConversation` checks transaction membership and attaches the same thread to a legitimate deal, including after listing deactivation; the transaction-created trigger also performs this handoff. A cancelled transaction does not delete its conversation. Only the buyer and seller can use conversation callables; direct Firestore reads/writes are denied, including to admins through client SDK rules. Admins receive bounded reported-message context only through `getAdminRecord` after claim authorization. Participants cannot choose sender, participant, listing or transaction IDs on writes.

The inbox fetches 20 conversations per page, and a thread fetches 20 messages per page. No global listener or unbounded history is used. Sending emits an existing in-app `message_received` notification to the other participant, subject to their notification preference. The mobile contract is a listing-context inbox row, private thread header, chronological messages and a 44px-or-larger composer action. There is no presence, typing indicator or rich media.

## Send retries and abuse controls

`sendConversationMessage` requires a random `idempotencyKey` of 16–128 ASCII letters, digits, underscores or hyphens. The composer preserves its key through a failed or uncertain send of the same normalized text, account and conversation. A confirmed send clears the key; editing the message or changing its scope starts a new logical send. This pending request is held in memory rather than persisted with account data.

The backend hashes the authenticated sender, conversation, action and request key into an opaque message ID. A private receipt under `users/{uid}/private/messageRequests/messageSendReceipts/{hash}` stores only the canonical body hash, message ID, server timestamp and a 24-hour cleanup deadline. It never stores the raw key or message body. All direct client reads and writes to receipts are denied. Same-key retries, including concurrent requests, return the existing message ID; changed content on that key fails closed. Removing or expiring a receipt cannot duplicate a retained message because its deterministic ID is checked in the same transaction. An orphaned receipt whose original message is missing also fails closed.

Only new logical sends consume the server-side message budget of 120 accepted sends per rolling 60 seconds. Eligibility, lifecycle, conversation membership and counterpart availability remain server-enforced. A successful retry consumes no additional quota and changes no preview, unread count or timestamp. The existing message-ID-based transactional notification and intelligence dedupe prevents trigger retries from duplicating those side effects. Throttled sends return a safe retry delay without revealing quota counters or account IDs.

The `expiresAt` deadline makes message receipts eligible for the separately prepared `messageSendReceipts` TTL policy; physical expiry requires the operator to activate that policy. This code does not activate a cloud TTL policy or schedule. Account deletion's existing recursive user cleanup removes receipt and cadence metadata, including nested records beneath missing parent documents. These short-lived operational records do not change marketplace conversation retention.

Reports for conversations and messages use the existing `reports` collection through `submitMarketplaceReport`. Only participants can report them, and message reporters cannot report their own messages. The deterministic reporter-target ID prevents repeated spam reports. Admin report detail can view the reported message and up to 20 recent context messages, then record status, resolution and private internal notes. These notes are never returned through user callables.

## Current privacy and retention behavior

- `getConversation`, `getConversations` and `getConversationMessages` require Firebase Auth and check that the caller is the stored buyer or seller. `sendConversationMessage` and `markConversationSeen` perform the same check. Firestore rules deny all direct conversation/message access, including direct admin-client access. Sender ID and timestamps come from the server, not the caller.
- A listing must be active and eligible to **start** a listing conversation. An existing conversation remains readable and sendable after the listing becomes inactive while both accounts remain available and the conversation is open. A verified transaction can attach or access the same buyer/listing thread after deactivation; it does not create a second thread. Transaction completion, cancellation and dispute do not by themselves close a thread. Account-deletion cleanup closes affected conversations and replaces their paths/participant identity with an opaque deletion identity; there is no user-facing close or reopen action.
- Account deletion erases departing users' authored message bodies/media and conversation previews/copied images. Counterparty-owned messages follow the implemented deal-closure +90-day deadline; no-deal history expires within 90 days of cleanup. Relevant report/dispute evidence is separately restricted and expires after case closure +180 days. Cleanup retries do not extend existing deadlines. The implementation, pending-obligation behavior, retention worker and production execution safeguards are documented in [account-deletion.md](account-deletion.md). Message editing, individual-message deletion and export controls are not implemented.
- Firestore retains the conversation document (including short latest-message preview, unread counts and timestamps), full message bodies and sender IDs in its `messages` subcollection, and any submitted moderation reports with reporter/target IDs, reason, details, status, resolution and private notes. An in-app notification stores listing context and a generic message notice, not the message body. Marketplace intelligence may retain a message-started/sent **event without the message body** under its separately documented event retention behavior.
- Claim-authorized admins can inspect a reported conversation through the admin report-detail callable, which returns the reported message and at most 20 recent messages. This is moderation access, not unrestricted direct Firestore client access. Participants cannot read report state or internal notes. Backend operators with Admin SDK/IAM access remain outside client-rule restrictions.

Production activation and public policy publication remain separate release gates. Do not promise export or instantaneous backup/log erasure. This is not end-to-end encrypted messaging.

`tests/messaging-idempotency-emulator.integration.mjs` covers normal sends, uncertain/concurrent retries, content conflicts, scope separation, exact-once side effects, receipt expiry/removal, quota exhaustion, private-data access and lifecycle guards. `tests/legacy-category-emulator.integration.mjs` covers valid/missing/malformed categories, deleted listings and normal price-drop engagement without invented category analytics. Both use only disposable `demo-takeme` data.
