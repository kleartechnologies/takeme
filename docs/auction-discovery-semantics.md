# Auction discovery price and inventory

An auction's `startingBid` is a positive integer number of MYR sen and remains the initial bid threshold. Zero is invalid in the existing server validator and Firestore schema. The observed RM0 local item is invalid fixture/legacy data, not a free-auction product rule; active discovery excludes it. No production records were changed.

Cards/detail display `currentBid` when `bidCount > 0`, otherwise `startingBid`, explicitly labelled “current bid” or “starting bid”. The indexed `listings.price` field is the mixed-feed discovery amount in ringgit: starting bid at creation, updated atomically to the accepted current bid by `placeBid`. Thus price sort and maximum-price query match what buyers see; fixed-price listings retain their listed price. `currentBid` and `startingBid` remain integer-sen auction authority and bid validation never relies on `price`.

Existing auctions created before the Phase 14B bid-path update may retain their original `price = startingBid / 100` after a bid, even though `currentBid` and `bidCount` were updated. `listings.price` is the indexed sortable/filterable **derived discovery price in MYR**, not a transaction amount. `startingBid` and `currentBid` are authoritative integer sen; accepted bids also live in the immutable bids subcollection. A no-bid auction should have `price = startingBid / 100`; an auction with bids should have `price = currentBid / 100`. Existing `buy_now_and_auction` records, if present, need product/schema review before inclusion because their fixed-price side may have different semantics.

## Deterministic, idempotent reconciliation plan — not executed

1. Schedule a separately approved production run **after** the Phase 14B `placeBid` Function is deployed, so new bids maintain the derived price during reconciliation. Inventory `listings` with `listingType == "auction"` in bounded pages. Export the candidate IDs and current field values to a restricted audit artifact; take a recoverable database backup. Bid documents may be read for validation, but do not mutate transactions, bids, GMV, `finalBid`, `startingBid`, `currentBid`, or auction lifecycle fields.
2. For each listing, require a positive safe-integer `startingBid`, a nonnegative safe-integer `bidCount`, and a finite stored `price`. If `bidCount == 0`, require `currentBid == 0` (or an explicitly reviewed legacy null representation) and derive `startingBid / 100`. If `bidCount > 0`, require a positive safe-integer `currentBid >= startingBid`; compare it with the highest recorded immutable bid amount and derive `currentBid / 100` only when they agree. Check any winner/finalBid inconsistency separately; **skip and flag** ambiguous or malformed records instead of guessing or reducing a legitimate bid.
3. Dry-run first: report totals for already-correct, would-update and skipped records, with IDs and old/new derived prices. Have an operator review exceptions and historical completed/cancelled examples. Do not use listing `price` as a source for transaction/GMV repair.
4. For an approved write run, process small bounded batches. In a Firestore transaction, reread each candidate and its highest recorded bid, then re-evaluate the same guards against current `bidCount`, `currentBid`, `startingBid` and `listingType`. If `price` already equals the derived value, make no write. Otherwise update **only** `listings/{id}.price`. If the document changed between scan and transaction, retry/recompute or skip; never apply a stale scanned amount. Preserve history and do not rewrite `updatedAt` merely for this derived repair.
5. Repeat the dry run after writes and verify zero remaining valid mismatches, the skipped-ID review queue, price-low/high and max-price discovery against representative auctions, and unchanged bid/transaction counts and amounts. Rerunning the write procedure is safe: matching records are no-ops. Deploy and execution require a separate production approval; this document is the plan, not a migration execution.

The active Explore feed additionally filters auction status, positive starting bid, valid current bid and `auctionEndAt > now` while paging. This guards against scheduler lag and malformed fixtures without changing the authoritative finalization scheduler. A scheduled auction may appear in discovery before bidding opens; expired/finalized/cancelled auctions do not appear as active inventory.

Discovery inventory queries require a confirmed server response. Firestore's default `getDocs` can return an empty cached result while offline, which would misleadingly say that the marketplace has no active listings. The active listing feed uses `getDocsFromServer`; a backend failure is shown as an error with retry, while a successful zero-result query alone produces the genuine empty state. This also applies to the home feed's fallback listing query.
