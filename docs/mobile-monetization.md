# TAKEME Boost + Featured — web and Flutter contract

Listings remain free. Boost means **more visibility in relevant discovery results**; Featured means **premium placement in a dedicated section**. Neither changes earned reputation, identity verification, transaction history or the Phase 6 organic recommendation score. The payment provider is **not configured**. Example package prices are shown for design/testing only; no request is charged or activated.

## Package and request model

`functions/src/promotion-domain.ts` owns fallback package definitions (Boost 24 hours RM2.90, Boost 3 days RM4.90, Featured 7 days RM9.90). Prices are integer sen and currency `MYR`. These are not approved launch prices. An admin can override duration, price, label or availability through `promotionPackages/{packageId}`; the server validates bounds and snapshots the chosen package into each new promotion. Web and Flutter get the catalog from `getPromotionPackages`, never from client pricing. Admin package documents are not public; the callable exposes only the curated catalog.

`promotions/{promotionId}` stores listing/seller/type/package IDs, status, payment status/provider, priceSen, currency, durationHours, startAt/endAt, impression/click counters, timestamps and a refund-review flag if a paid listing becomes unavailable. `promotionLocks/{listingId}` is server-only and permits at most one pending/scheduled/active request per listing. Cancelled and expired requests remain in bounded history. Clients cannot write either collection. The seller's history comes from the owner-verified `getMyPromotionRequests` callable (latest 10 for one listing); admin list access is claim-gated and bounded.

`createPromotionRequest` checks Firebase Auth, seller ownership, an active listing, an available auction when relevant, package availability and the lock in one transaction. It creates `pending_payment` + `not_configured`, with **null** start/end times and zero counters. User-supplied price/payment fields are ignored. `cancelPromotionRequest` can cancel only the seller's own unpaid, unconfigured request. Listing removal, sale, auction end or cancellation triggers `onPromotedListingUpdated` to cancel the attached promotion; a previously paid one is flagged for human refund review. The bounded hourly `expirePromotions` job expires verified active promotions after `endAt`; serving checks timestamps at read time too. `scheduled` and `active` are reserved for trusted payment integration—no current callable can activate them. Auction bidding/finalization remain separate.

## Payment boundary

There is no Stripe key, Checkout integration or verified payment webhook in this repository. The UI says “Payment integration not yet configured” and offers **Save promotion request — no payment**, not a Pay or success button. No card data is stored. A future Stripe adapter should create a server-side Checkout Session for the snapshotted amount, tie it to the promotion ID, and activate only after a verified provider webhook or equivalent server-side confirmation. A browser redirect or client `paymentSuccessful` field must never grant placement or revenue. The handler needs signature verification, idempotency, amount/currency match, seller/listing revalidation, auction end-time clipping, and a refund/cancellation policy. Do not use Stripe Connect or charge transaction commissions. Stripe's [Checkout Session API](https://docs.stripe.com/api/checkout/sessions) exposes payment status; [Stripe payment guidance](https://docs.stripe.com/payments/existing-customers) describes server-side fulfillment. This adapter is **future work**.

## Organic and paid placement

`getMarketplaceRecommendations` and its deterministic score are untouched by promotion. Paid placement is a separate `getPromotionPlacements` call over at most 24 **already retrieved** Explore candidates. The server re-reads canonical listings, verifies active/auction eligibility and category/title-search context, and considers only active, paid, in-window promotions. `allocatePromotionPlacements` inserts at most two paid listings per candidate page, only when there are at least four candidates per slot, with at most one selected promotion per seller and no duplicate listing. Featured receives priority over Boost; other listings retain organic order. A boosted washing machine cannot enter an iPhone result set merely because it paid. The homepage's separate `getFeaturedPromotions` section returns at most four active paid Featured listings from a bounded 12-document pool, one per seller. With no verified paid promotion the section is absent and the homepage is unchanged. Paid cards carry a subtle “Boosted · paid” or “Featured · paid” label, never a trust badge.

## Events, analytics and privacy

`BOOST_CREATED`/`FEATURED_CREATED` are written in the authoritative request transaction and mean **request created**, not purchased. `PROMOTION_IMPRESSION` and `PROMOTION_CLICK` use the Phase 6 private event log with promotion ID, listing ID and home/explore context. Counters update atomically only when the authenticated non-seller event passes one-hour dedupe, daily quota, and active/paid/listing/time checks. An impression is sent when a paid card enters the viewport; a click is sent when its listing link is tapped. These client-observed counts are directional, not payment evidence or guaranteed unique human views. Sellers cannot directly change events/counters or count their own listing. A determined third party could still automate traffic; monitor abuse and consider App Check before operational monetized metrics. Promotion events have zero interest weight and do not affect organic ranking.

`BOOST_STARTED`/`FEATURED_STARTED` are reserved for future verified activation; no fake start event is emitted. `BOOST_EXPIRED`/`FEATURED_EXPIRED` are server-written only after actual active promotion expiry. `BOOST_PURCHASED`/`FEATURED_PURCHASED` and revenue remain unavailable until verified payments exist. A future Admin Dashboard can group verified paid records by type/package/category and private events by exposure, but must not count pending requests as purchases or calculate GMV from listing prices/bids. Seller status shows actual impressions, clicks and end time only for an active promotion; no sale conversion is claimed.

## Cost, security and Flutter

Package lookup reads three fixed documents; seller history is limited to 10; placement re-reads at most 24 listings and 24 matching promotions; Featured reads at most 12 promotion/listing pairs. The expiry job processes at most 100 due records hourly and can continue on later runs. No global realtime listener, per-second timer, client polling, or event-per-scroll is added. Required indexes are in `firestore.indexes.json`. Firestore rules deny client mutation of promotions, locks, events and counters; admin control uses the existing `admin` claim.

Flutter should use the same regional Firebase callables and statuses, display the server catalog with example/final pricing flags, and render Boost/Featured as distinct touch-friendly choices. Treat `paymentAvailable=false` as a hard disabled checkout state. Never implement native client activation or duplicate pricing/placement formulas. Use at least 44 logical-pixel targets and the same loading, empty, unavailable and error states as web.

Run `node tests/promotions-emulator.integration.mjs` with the `demo-takeme` Auth/Firestore/Functions emulators, plus Functions/unit/auction/intelligence/trust tests, lint, TypeScript and production build. The paid fixture in that emulator test is created by Admin SDK **only to verify the gate**; product code has no fake-payment path. Do not deploy from this phase. Before any later rollout, confirm final prices, Stripe account/webhook, tax/refund policy, index readiness, functions/rules, fraud monitoring, App Check and a production checkout QA plan.
